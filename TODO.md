## Needs a decision

### Data and estimates

- [ ] **WITH / COVAR edges never carry estimates.** `attachEstimates` in `app/src/model/graph.ts` attaches only codes 1 and 11 to edges. Code-2 and code-12 rows are matched but not stored, though the same function builds COVAR edges from code-2 rows, so every covariance edge shows no number and indeterminate significance. Evidence that code 2 is the unstandardized covariance and code 12 its STDYX form (a correlation): code 12 equals code 2 divided by the square root of the two code-4 residual variances, which held for every non-sentinel pair checked (in `dgm/syn_sem.dgm`: `2 1 c4 b4 0.123`, residual variances 0.433 and 0.441, so 0.123 / sqrt(0.433 x 0.441) = 0.281 against `12 1 c4 b4 0.282`), and the Mplus User's Guide v8 (ch. 18) says residual covariances are standardized by residual variances. Mplus does not publicly document the `.dgm` codes. The codes fit a scheme: last digit = parameter type (1 loading or regression, 2 covariance, 4 residual variance, 5 latent variance); tens digit = estimate type (0 unstandardized, 1 STDYX, 2 STDY, 3 STD). 2x codes appear in output run with `OUTPUT: STANDARDIZED` (all three standardizations); whether `OUTPUT: STDYX` alone omits them is not checked. Decision: confirm. Proposed: attach 2 to `unstd` and 12 to `stdyx` on WITH/COVAR edges, by analogy with 1/11.
- [ ] **How 2x (STDY) rows are handled.** `attachEstimates` in `app/src/model/graph.ts` matches 2x rows to edges but stores nothing from them; an unmatched 2x row other than a covariance synthesizes an ON edge; and code 21 (STDY loading or regression) is missing from `DIRECTED_CODES`, whose doc comment lists only 1, 11 and 31. Decision: add 21 to the directed codes (proposed: yes), and whether STDY estimates are ever shown.
- [ ] **A model with no latent variables loses every estimate (bug, found 2026-10-16).** `parseEstimateSection` in `app/src/parser/dgm.ts`. Mplus writes a groupings count of 0 in the `.dgm` header when there are no latents (User's Guide `ex3.11`, a path analysis); the code-1 rows that follow are intact, but the parser returns no estimates, so every path renders without a coefficient. Correct behaviour is clear: parse the rows. Needs a fix and a regression test (a synthetic path-analysis fixture in `dgm/`).
- [ ] **Estimate rows without a standard error are dropped.** `parseEstimateRow` in `app/src/parser/dgm.ts`. Some Mplus output writes rows with no SE column (for example `1 1 f y1 -0.476`, 5 tokens); a file made of such rows loses every estimate. The corpus test only checks `estimates.length > 0`. Decision: support no-SE rows with `se: null` and indeterminate significance? A 5-token no-SE row is ambiguous with the 5-token variance layout.
- [ ] **Significance ignores the coefficient mode.** `isSignificant` in `app/src/model/significance.ts` always prefers `unstd`. In STDYX mode a loading fixed at 1 (unstandardized SE 0) shows indeterminate even when its STDYX estimate has a large t statistic. Decision: should significance follow the active mode?
- [ ] **Mplus list ranges (`y1-y3`) are not expanded, and unmatched estimate rows always become ON edges. Raised in priority 2026-10-16:** Mplus's own User's Guide examples rely on ranges (`ex5.1`: `f1 BY y1-y3;`), and their `.dgm` files render as one BY edge to a node named `y1-y3` plus ON edges carrying the loadings (`ex5.1`, `ex5.6`, `ex5.11`). Mplus expands a range by the order of the variable list. `parseTermList` in `app/src/parser/dgm.ts`; the fallback in `attachEstimates` in `app/src/model/graph.ts`. Decision: expand ranges from `NAMES` order? Infer BY or COVAR in the fallback from the groupings header and the code?
- [ ] **Single-indicator latents break groupings detection; node kind fixed at first sight.** `parseEstimateSection` / `looksLikeVariableList` in `app/src/parser/dgm.ts`; node creation in `buildGraph` in `app/src/model/graph.ts`. Decision: accept single-name indicator lines, and upgrade a node to latent when it later appears as a BY left-hand side?
- [ ] **Multi-group and mixture models.** `%OVERALL%` and `MODEL g2:` labels become nodes (`parseDgm` / `parseModelBlock` in `app/src/parser/dgm.ts`); group estimates overwrite each other (`attachEstimates` in `graph.ts`, `buildPValueMap` in `parser/out.ts`). No fixture in `dgm/` uses these. Decision: scope of multi-group support.
- [ ] **`y1*0.5@1` sets both `free` and `fixed`.** `applyModifiers` in `app/src/parser/dgm.ts`, whose doc comment lists `*0.5@1` as an example. Decision: precedence rule. Proposed: `@` wins (fixed, not free), since a fixed parameter cannot also be free.
- [ ] **Mplus abbreviated keywords are not recognised.** `USEV = ...` gives an empty use list (the NAMES/USEVARIABLES patterns in `parseDgm`, `app/src/parser/dgm.ts`). Mplus accepts abbreviations of option keywords. Decision: support abbreviations generally (minimum-prefix matching) or only common ones such as `USEV`?
- [ ] **Constraint-label codes are 90 + parameter type; only 91 is read (settled by an Mplus 8.11 run, 2026-10-22).** A synthetic model with labelled loadings, two covariances sharing a label (`c4 WITH b4 (cv); x1 WITH x2 (cv);`) and labelled residual variances wrote `91 1 fa a2 la`, `92 1 c4 b4 cv` and `94 1 a1 rv` (95 labels latent variances, seen in User's Guide `ex5.20`). So: code 91 is directed and should join `DIRECTED_CODES` in `app/src/model/graph.ts`; code-92 rows are dropped by `parseEstimateRow` (`app/src/parser/dgm.ts`), so equality labels on covariances never reach WITH/COVAR edges; 94/95 rows are dropped harmlessly until variances are drawn. Correct behaviour is clear: parse 9x label rows, attach 91 to directed edges and 92 to covariance edges; add 92/94/95 to the allow-list. Probe input: `_scratch/synth-corpus/syn_label.inp` (local); move it to `tools/mplus/synthetic/` with a committed fixture when fixing.
- [ ] **Unmatched standardized covariance rows become ON edges.** In `attachEstimates` (`app/src/model/graph.ts`) only an unmatched code-2 row synthesizes a COVAR edge; an unmatched 12, 22 or 32 row falls back to an ON edge. Real Mplus output always writes code 2 before 12/22/32, so this only bites files where the unstandardized row is missing. Decision: treat every covariance code (last digit 2) like code 2 when synthesizing? Proposed: yes. (Deferred by the 2026-10-17 fix batch, F1.)
- [ ] **Group-specific MODEL sections are dropped.** Since 2026-10-17 `parseModelBlock` (`app/src/parser/dgm.ts`) ends the overall MODEL block at the next command header, including `MODEL g2:`, so group-specific statements are no longer read (before, they produced garbage edges such as a node named `model`). Part of the multi-group decision above; no multi-group fixture yet. The command-header keyword list is from memory, not checked against the User's Guide.
- [ ] **A second `.out` merges into the first one's p-values.** `setPValues` in `app/src/state/store.ts`. Edges missing from the new run keep stale p-values. Decision: replace or merge? Proposed: replace.

### Canvas and interaction

- [ ] **Canvas fit policy.** `fitViewBox` in `app/src/main.ts` with `contentViewBox` in `app/src/ui/viewBox.ts` refit the view to the content after every change. A small graph is scaled up to fill the canvas (two nodes about 3x), and dropping a node near the edge re-zooms and re-centres the whole diagram. Proposed (as in draw.io, yEd): fit on load and on Re-run layout, never zoom past 1:1 using the measured canvas size, and during edits only grow the view, never shrink or re-centre it.
- [ ] **WITH / COVAR style shown wrongly in the inspector.** The renderer (`app/src/render/svg.ts`) forces WITH/COVAR edges dashed and arrow-less outside the style cascade (`deriveEdgeBase` in `app/src/render/styles.ts`), so the inspector shows "Solid" and choosing "Solid" does nothing. Proposed: make dashed and arrow-less the kind's default in the effective style, and honour an explicit "Solid". (Superseded in part by the style-preset redesign: Mplus default is a curved double-headed arrow.)
- [ ] **Covariances in the layout.** WITH/COVAR edges are given to ELK as directed edges, so they influence layering and get orthogonal routes. Leaving them out and drawing curves was tried and reverted on 2026-10-16: the curves cut through nodes stacked in one column. Covariance placement belongs to the SEM-aware layout in the style-preset redesign.
- [ ] **"Re-run layout" wipes styles, p-values and selection, and clears undo.** The Re-run layout handler and `runLayout` in `app/src/main.ts` -> `loadGraph` in `app/src/state/store.ts`. Decision: keep styles and p-values (new `applyLayout` action that replaces only layout and positions), and should relayout be one undoable step? Proposed: keep them, make it undoable.
- [ ] **Edges keep their original ELK bend points after a node moves.** Edge geometry and `computePath` in `app/src/render/svg.ts`; most layout edges have bends, so moved nodes get lines that double back. Decision: drop bends for edges touching a moved node, shift them, or re-route?
- [ ] **Dropping several files at once handles only the first, in OS order.** The window drop handler in `app/src/main.ts` reads only the first file. A `.dgm` dropped together with its `.out` can be rejected ("Load a .dgm file before attaching a .out file") and the `.dgm` silently ignored. Decision: handle all dropped files with the `.dgm` first, or reject a multi-file drop with an error? Proposed: handle all, `.dgm` first.
- [ ] **Inspector width control cannot show or keep magnitude-scaled widths above 10.** The stroke-width slider in `app/src/ui/inspector.ts` has max 10, while the effective width with magnitude scaling is `baseEdgeWidth + magnitudeScale x |coef|` (for example 16.5). One arrow-key nudge stores 9.9. Decision: raise the max, or treat scaled edges differently (for example edit the base width, not the effective width)?
- [ ] **The file picker disappears after the first load.** `handleFile` in `app/src/main.ts` hides the dropzone, which holds the file picker, so a `.out` or another `.dgm` can only be dropped afterwards. Decision: keep an "Open file" control in the toolbar?
- [ ] **Concurrent loads can finish out of order (suspected, low).** `handleFile` and `runLayout` in `app/src/main.ts`. Decision: guard with a load-generation counter?
